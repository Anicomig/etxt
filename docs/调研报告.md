# 加密 txt 编辑器方案调研

> 调研日期：2026-11-11
> 目标机器：Windows 11 25H2 (build 26200)，Python 3.14.4，Typora 1.9.5，Store 版记事本 11.2607.14.0
> 本文所有结论均为**本机实测**，非文献推断。标注「未确证」的是没有实测到的部分。

---

## 一、需求重述

双击一个文件 → 弹出密码框 → 密码正确 → 用编辑器打开明文 → 编辑保存 → 关闭后自动重新加密写回原文件、删除临时明文。

威胁模型（用户确认）：**防文件被随手翻看、云同步、拷走**。不要求防同机进程读内存。

---

## 二、核心结论（先说最重要的）

**需求原样可做，但"用系统记事本"这一条必须放弃。**

实测发现 Win11 的 Store 版记事本有三个硬伤，其中第三个直接破坏加密目的：

### 硬伤 1：单实例多标签，窗口不等于文档

记事本 11 是**单实例、单窗口、多标签**。第二次打开文件不会产生新窗口，而是往已有窗口里加标签。

实测：连续打开 3 个文件，系统里只有 **1 个** `Notepad` 类窗口（hwnd `2231476`），标题只显示**当前活动标签**的文件名。

后果：**"检测到记事本窗口关闭"这个信号不可用**。用户关掉一个标签，窗口还在；用户开着 10 个标签，其中一个是我们解密的文件，窗口标题显示的是别人的文件名。任何基于窗口标题/窗口存在性的判断都会误判。

> 用户已说明会手动关标签页，但这只解决了"我该什么时候加密回去"，没解决程序如何**知道**该加密回去。

### 硬伤 2：进程不可等待

`C:\Windows\System32\notepad.exe` 只是入口 stub。实测 `subprocess.Popen` 启动后该 PID **立刻退出**，退出码 `3221225477`（`0xC0000005`，即 `STATUS_ACCESS_VIOLATION`），而真正的编辑器进程是另一个 PID。

后果：`wait()` / `RunWait` / `$process.HasExited` 全部失效，无法用"等进程结束"来判定编辑完成。

### 硬伤 3（决定性）：未保存的明文会落盘

记事本 11 会把**正在编辑但尚未保存**的内容，以 **UTF-16 明文**写入：

```
%LOCALAPPDATA%\Packages\Microsoft.WindowsNotepad_8wekyb3d8bbwe\LocalState\TabState\<guid>.bin
```

实测证据（探针 `np8` / `np9` / `np14`）：

| 场景 | TabState 里是否有明文 | 关闭后 |
|---|---|---|
| 只打开、不编辑 | 无 | 无 |
| 编辑后**保存**（Ctrl+S） | **有** | 文件保留 |
| 编辑后不保存、正常退出点「不保存」 | **有** | **文件保留** |
| 编辑后不保存、强制结束进程 | **有** | **文件保留，重启后内容被恢复** |

最严重的一条：`np9` 测试中，用户明确点了「不保存」，应用正常退出后，明文仍在 `TabState\b34a68c6-....bin` 里；重启记事本，那个标签页连同未保存的内容一起回来了。

**这直接违背加密的目的**：解密出来的敏感内容，会被一个我们无法控制、无法预期、且默认开启的自动恢复机制，以明文形式复制到用户目录下。

> 注：`np14` 中「正常退出」后 TabState 被清理了。两次结果不一致的原因是我在 `np9` 里有多标签共存、`np14` 里是单标签。**结论按最坏情况取**：多标签场景下明文会残留。

## 三、Typora 评估（用户提议的替代）

Typora 1.9.5 已安装在 `D:\Program Files\Typora\Typora.exe`。

### 优点（实测确认）

| 项目 | 实测结果 |
|---|---|
| **.txt 支持** | ✅ 原生支持，且**按原始文本处理**，不做 Markdown 渲染 |
| **字节保真** | ✅ 首行空格、`#` 开头行、行尾空格、CRLF、无末尾换行 —— 全部原样保留 |
| **单文件单窗口** | ✅ 每个文件独立 hwnd，关闭窗口 = 关闭文档 |
| **可等待进程** | ✅ 主进程存活，`Popen.poll()` 可用 |
| **关闭自动保存** | ✅ WM_CLOSE 后 0.5s 内自动落盘，**无保存提示框** |
| **实时自动保存** | ✅ 编辑后数秒内直接写入原文件 |

字节保真实测：写入 `第一行中文 / "  leading spaces" / "tab\there" / "# looks like heading" / "**bold?**" / "trailing   " / 无末尾换行`，关闭后逐字节比对，全部保留。

### 致命缺点（实测确认）

Typora 同样会泄漏明文，且泄漏点**更多**：

1. **`%APPDATA%\Typora\draftsRecover\`** —— 定时把文档内容快照成 `<日期> <文件名> <时间>.md`。实测每次打开/编辑都会生成新的快照文件，内容就是**当前文档明文**。

   实测：打开 `draftleak2.txt`（内容 `plain seed line`），输入后，`draftsRecover` 立刻出现 `2026-11-11 draftleak2 224744.md`（15 字节，就是原文）。

2. **`%APPDATA%\Typora\backups\sum`** —— JSON 索引，记录**每个打开过的文件的完整绝对路径**、窗口位置、是否未保存。

   实测内容：
   ```json
   {"innormalQuit":true,"windows":[{"path":"F:\\...\\draftleak2.txt",
     "hasUnsaved":false,"mountFolder":"F:\\...\\probe_tmp", ...}]}
   ```
   即：**文件名和路径会被永久记录**，即使内容加密了，元数据仍然泄漏"这个人在编辑哪个文件"。

3. **`%APPDATA%\Typora\typora.log`** —— 明文日志，记录每次启动的完整命令行和读取的每个文件路径。

   实测内容：
   ```
   INFO 2026/11/11 22:47:31  launch with argv [D:\Program Files\Typora\Typora.exe, F:\...\draftleak2.txt]
   INFO 2026/11/11 22:47:32  [RenderProcess 1][Log] readContentFrom F:\...\draftleak2.txt
   ```
   **只泄漏路径，不泄漏内容**（已逐行确认），但日志会持续累积（实测 159KB / 501KB 两个日志文件）。

4. 进程退出后 `draftsRecover` 的文件**不会自动删除**（实测残留 178 个历史文件）。

### Typora 结论

**比记事本好，但同样不满足"不留明文"的要求。**

不过 Typora 有一个记事本没有的优势：**它是可以关闭的**。用户可以接受"用完 Typora 就把 `draftsRecover` 清空"这个操作，而记事本的 `TabState` 是系统级自动恢复机制，用户无法可靠控制。

## 五、推荐方案

### 方案 A（推荐）：Python 自研壳 + 内置编辑器

**理由**：
- 完全闭环，明文只存在于内存和短暂存在的临时文件
- 不依赖任何第三方编辑器的自动保存/恢复行为
- 本机 Python 3.14.4 + `cryptography` 48.0.0 已就绪，零安装
- 可以做"双击即开"的文件关联

**技术选型（均已实测可用）**：

| 环节 | 选型 | 实测数据 |
|---|---|---|
| 加密算法 | AES-256-GCM (`cryptography`) | 100KB 加解密 0.043ms |
| 密钥派生 | scrypt n=2^15, r=8, p=1 | **81.7ms/次**（防暴力破解的合理代价） |
| 密码框 | tkinter（Python 自带） | ✅ 可用，屏幕 2560x1440 |
| 原子写回 | `os.replace()` | ✅ 同目录原子替换可用 |
| 篡改检测 | AES-GCM 自带 | ✅ 改 1 字节即 `InvalidTag` |
| 保存检测 | `st_mtime_ns` 轮询 | ✅ 1ms 级分辨率可用 |

**文件格式设计**：

```
magic   : b"ETXT1\0"      (6 bytes)
salt    : 16 bytes         (scrypt 盐)
nonce   : 12 bytes         (GCM nonce)
ct+tag  : 剩余             (密文 + 16 字节 GCM tag)
```

AAD 绑定文件名，防止把 A 文件密文改名冒充 B 文件。

**为什么不用内置编辑器而是用"临时文件 + 外部编辑器"**：
如果坚持要"用某个外部编辑器"，就必须处理该编辑器的泄漏问题（见第二、三节）。而自带一个简易文本编辑器（tkinter Text 组件）可以彻底避免这个问题。代价是没有语法高亮等高级功能。

**如果要保留 Typora 体验**：用方案 B。

### 方案 B：Python 壳 + Typora，附加清理

在方案 A 基础上，把"内置编辑器"换成"调用 Typora"，并增加：

1. 启动前记录 `%APPDATA%\Typora\draftsRecover\` 的文件快照
2. 关闭后删除**新增的** drafts 文件（只删本次产生的，不动用户历史）
3. 从 `backups\sum` 里移除本次文件的路径记录
4. 清理临时明文文件
5. 可选：`typora.log` 里的路径行无法安全删除（会破坏日志连续性），只能接受或定期清空

**风险**：如果 Typora 崩溃，drafts 可能残留。清理逻辑必须放在 `try/finally` 里，且要有独立的"清理残留"入口。

**注意**：Typora 的 `draftsRecover` 在本次调研中已经积累了大量历史文件（178 个），说明这个目录本身就在长期堆积用户文档内容。如果用户本来就用 Typora 编辑普通文档，这个泄漏是既有事实，不是本方案引入的；但**加密文件的明文被复制进去，是新增的风险**。

### 方案 C（不推荐）：坚持系统记事本

技术上可做，但必须接受：

- **无法可靠检测关闭时机** → 只能轮询临时文件 mtime，延迟数秒
- **明文会进 `TabState`** → 需要在每次编辑后扫描并删除相关 `.bin`
- **多标签场景下 TabState 内容无法精确归属** → 可能误删用户其他标签的恢复数据

**如果用户坚持，正确做法**：
1. 不用"窗口关闭"作为信号，改用**临时文件 mtime 轮询 + 空闲超时**
2. 每次写回后，扫描 `TabState`，删除包含本次明文的 `.bin`
3. 明确告知用户：强杀进程/断电时明文可能残留

## 六、实现要点（方案 A 详细）

### 6.1 触发方式

推荐**专用扩展名**（如 `.etxt`），理由：
- 不干扰普通 `.txt`
- 双击即走加密流程，无需右键
- 文件图标可区分

注册位置（**HKCU，无需管理员**，已实测可写）：
```
HKCU\Software\Classes\.etxt           -> "EtxtEncrypted.Document"
HKCU\Software\Classes\EtxtEncrypted.Document\shell\open\command
    -> "pythonw.exe" "C:\path\etxt.py" "%1"
```

如果用户坚持保留 `.txt` 后缀，则只能走右键菜单，或改 `.txt` 的 UserChoice（会影响所有 txt）。

### 6.2 关键流程

```
双击 .etxt
  → 读取文件头，校验 magic
  → 弹出 tkinter 密码框（掩码显示）
  → scrypt 派生密钥（~82ms）
  → AES-GCM 解密，验证 tag
      ├─ 失败 → 提示"密码错误或文件损坏"，退出
      └─ 成功 → 继续
  → 写入临时明文文件（%TEMP%\etxt_<random>.txt，随机名防猜测）
  → 启动编辑器，等待关闭
  → 检测到关闭 → 读回临时文件内容
  → 重新加密 → 原子写回原 .etxt
  → 安全删除临时文件（覆写 + 删除）
```

### 6.3 已实测的坑（必须避开）

| 坑 | 实测现象 | 对策 |
|---|---|---|
| **沙箱内无法启动 GUI** | `subprocess.Popen(["notepad.exe"])` 退出码 `0xC0000005` | 脚本必须在沙箱外运行；或用 MCP 通道启动 |
| **`SetForegroundWindow` 被拒** | 键盘输入跑到别的窗口 | 用 `AttachThreadInput` 或 MCP 的 foreground 派发 |
| **Typora 是 Chromium** | 无 UIA `DocumentControl`，`GetValuePattern` 超时 | 不能靠 UIA 读内容，只能读文件 |
| **记事本进程不可等待** | PID 立刻退出 `0xC0000005` | 改用窗口/文件信号 |
| **记事本单实例多标签** | 3 个文件只有 1 个窗口 | 不能用窗口标题判断 |
| **`Popen` 默认管道被沙箱阻断** | `Access to the path '\\.\pipe\...' is denied` | 用文件重定向，不要用 `capture_output=True` |
| **`Start-Process -Wait` 会被 GUI 子进程挂住** | 探针脚本 120s 超时 | 不要用 `-Wait`，改为轮询结果文件 |

### 6.4 安全细节

- 临时文件放在 `%TEMP%` 下**随机命名**，不要用原文件名
- 临时文件权限设为仅当前用户可读（`icacls`）
- 删除时先覆写再删（`os.remove` 前写入随机数据）
- 密码不落盘、不写日志
- 密钥派生用 scrypt（已验证 81.7ms，足够慢）
- 每次加密用新的 salt + nonce（GCM 的 nonce 绝不能重用）
